1. Micro Frontend

Bringing microservices thinking to the frontend layer

Micro Frontend decomposes a large application into smaller, domain-aligned frontends, each independently developed and deployed. The model carries the "end-to-end team ownership" principle from microservices into the UI layer.

  • A single team owns one domain — Search, Checkout, or Account.
  • Reduced coupling across codebases, release cycles, and backlogs.
  • Autonomy over integration: teams move independently without shared bottlenecks.

Why Module Federation?

The intersection of team autonomy and seamless integration

Product perspective

  • Domain roadmaps become clearer; teams progress without waiting on each other.
  • Individual product areas release independently without touching the entire frontend.
  • Capabilities are reused across multiple lines of business with less friction.

Engineering perspective

  • No publish-and-rebuild cycle before consumers can use updated modules.
  • Heavy dependencies such as Angular or React are shared to prevent duplicate loading.
  • The familiar module system and runtime loading model are preserved for developers.
3. Webpack Foundation

Webpack already had the building blocks for federation

🕸️

Dependency Graph

Webpack analyses import and export statements to construct a full dependency tree across all modules.

🧊

Chunk Splitting

Code is partitioned into discrete chunks that can be loaded asynchronously on demand.

⚙️

Runtime Loader

The browser-side runtime knows how to fetch chunks, resolve module references, and execute factory functions.

Key Insight

Module Federation is not a standalone mechanism bolted on from the outside. It is a principled extension of Webpack's existing chunk loading and runtime resolution infrastructure.

Webpack Mechanics

From local module resolution to remote module loading

Without Federation

import Button from './Button' → webpack resolves local path → bundles into a local chunk → runtime loads the local chunk → executes module factory

With Federation

import('remoteApp/Button') → runtime identifies remote reference → loads remoteEntry.js → initialises shared scope → calls get('./Button') on container → executes factory like a local module

The developer experience remains largely unchanged. What shifts is the module source — from a locally bundled chunk to a remote container resolved at runtime.

4. Module Federation Core Concepts

Host, Remote, and Shared

These three concepts explain most of the architecture: the host consumes modules, the remote publishes modules via a container, and shared manages dependency deduplication and version resolution.

🏠

Host

The application that consumes remote modules and renders them within its own UI.

🌍

Remote

The application that exposes modules via a container entry file such as remoteEntry.js.

🔗

Shared

A pool of shared dependencies — such as React or common utilities — that prevents redundant loading.

Runtime Components

The essential technical vocabulary

Container

The runtime object representing the remote application, typically registered on window[scope].

remoteEntry.js

The entry manifest and bootstrap code that tells the host what the remote exposes and how to call into it.

init()

Synchronises the shared scope between host and remote before any module is fetched.

get()

Returns the factory function for an exposed module; the host invokes the factory to obtain the actual module export.

await __webpack_init_sharing__('default') await container.init(__webpack_share_scopes__.default) const factory = await container.get('./Button') const Module = factory()
5. Runtime Mechanics

End-to-end sequence from import call to render

1

Resolve

The host encounters a remote import and identifies the target container.

2

Load

The browser fetches remoteEntry.js from the remote application.

3

Init

Host and remote perform a handshake to align on shared dependency versions.

4

Get

The host calls get('./module') to receive a factory function.

5

Execute

The factory runs, the module is evaluated, and it renders like local code.

In short: Module Federation = remote code loading + dependency sharing + container contract at runtime.

Deep Dive · Configuration Phase

Declaring the federation contract in webpack.config.js

Remote Application

Declares which modules it exposes and the entry filename consumers will reference.

new ModuleFederationPlugin({ name: "remoteApp", filename: "remoteEntry.js", exposes: { "./Button": "./src/components/Button" }, shared: ["react", "react-dom"] })

Host Application

Maps remote names to their runtime URLs so the module system can resolve them at load time.

new ModuleFederationPlugin({ name: "hostApp", remotes: { remoteApp: "remoteApp@http://localhost:3001/remoteEntry.js" }, shared: ["react", "react-dom"] })
Deep Dive · Build Phase

What webpack generates per application during the build

📁

Application Bundles

Standard output chunks for the application itself — split and optimised exactly as they would be without federation.

📋

remoteEntry.js

The container entry point: a manifest of every exposed module, the chunk IDs that back them, and the bootstrap code consumers invoke to load them.

⚙️

Runtime Code

Webpack-generated logic for managing the shared scope, coordinating version negotiation, and orchestrating asynchronous module loading across application boundaries.

Each application builds fully independently. The federation contract is resolved at runtime, not at build time — which is what enables independent deployment.

Deep Dive · Runtime Loading

Four operations from import call to usable module

1

Load Container

The host dynamically injects the remote entry script into the document head.

const script = document.createElement('script'); script.src = 'http://localhost:3001/remoteEntry.js'; document.head.appendChild(script);
2

Initialise Shared Scope

The host passes its shared dependency registry to the remote container.

await remoteApp.init( __webpack_share_scopes__.default );
3

Retrieve Module Factory

The host calls get() to obtain a factory function for the requested module.

const factory = await remoteApp.get('./Button');
4

Evaluate Module

The factory is invoked to produce the actual module export, ready for use.

const Button = factory().default;
Deep Dive · Shared Dependency Management

Version negotiation and singleton enforcement at runtime

  • Version comparison: Webpack runtime compares the version requirements declared by both host and remote.
  • Best-match selection: The highest mutually compatible version is chosen and loaded exactly once.
  • Singleton guarantee: When singleton: true is set, only a single instance is permitted across the entire application boundary.
  • Version contract: requiredVersion enforces a strict semver range — a mismatch triggers a warning or error at load time.

Singleton configuration example

shared: { react: { singleton: true, requiredVersion: "^18.0.0" }, "react-dom": { singleton: true, requiredVersion: "^18.0.0" } }
Deep Dive · Independent Deployment

Updating a remote without rebuilding the host

When a remote application is updated and redeployed, the host automatically loads the latest version of its modules on the next page load — without requiring its own rebuild or redeployment. This is the defining advantage of runtime federation over build-time package integration, and it is what enables truly independent delivery at scale.

📦

Build-time Package

The consumer must republish the dependency and rebuild to receive any change from the producer.

⚡

Module Federation

The remote deploys independently. The host picks up the change on the next load with no rebuild required.

🎯

Business Value

Each team controls its own release cadence with zero coordination overhead at the deployment level.

Reference · loadComponent Pattern

The canonical pattern for dynamic remote loading

function loadComponent(scope, module) { return async () => { await __webpack_init_sharing__('default'); const container = window[scope]; await container.init( __webpack_share_scopes__.default ); const factory = await container.get(module); return factory(); }; }

Line-by-line walkthrough

  • init_sharing: Initialises and populates the default shared scope.
  • window[scope]: Retrieves the remote container registered by remoteEntry.
  • container.init: Informs the remote which shared dependencies are available for reuse.
  • container.get: Returns a factory — not the final module — which must then be called to evaluate the export.
Shared Dependencies

3️⃣

Optimise Bundle Size

Remote bundles remain self-contained, yet the runtime has the opportunity to deduplicate shared portions at load time.

Build-time vs. Runtime

A comparison to avoid confusing federation with npm packages

Build-time Integration

  • The consumer installs the dependency before building.
  • Updating the producer typically requires republishing and rebuilding every consumer.
  • Well-suited to stable libraries with infrequent runtime changes.

Runtime Federation

  • The consumer loads the module from a remote URL while the application is running.
  • The producer deploys independently; the host does not need to rebuild.
  • Designed for micro frontend architectures with independent domain release cycles.
6. Adoption Guidance

Not every frontend challenge requires federation

Strong signals to adopt

  • Multiple teams co-developing a single product platform.
  • A requirement to release by domain or business capability independently.
  • Shared UI modules needed across teams without coupling release cycles.

Signals to defer adoption

  • A single small team with a straightforward release cadence.
  • Insufficient discipline around API contracts, versioning, and observability.
  • The real need is a reusable component library rather than independent deployment.
Executive Summary

The complete picture in under 60 seconds

"Micro Frontend is an architectural approach that divides the frontend by business domain so that teams can work independently. There are many ways to implement it, but Module Federation stands out because it allows one application to consume modules from another at runtime. Webpack makes this possible because it already has a runtime loader, a chunk system, and a module graph. Module Federation extends that infrastructure with containers, remote entries, and a shared scope."
